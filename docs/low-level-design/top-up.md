# Пополнение через Platega

В личном кабинете доступны сумма в целых рублях от 100 до 10 000 ₽ и способы оплаты магазина. По умолчанию доступны СБП и карта. Четыре стартовых пресета — 100, 300, 500 и 1000 ₽.

Браузер создаёт UUID попытки и передаёт его в `POST /api/me/top-ups`. При повторе с тем же UUID сервер возвращает текущую попытку. Перед запросом к Platega он сохраняет попытку в PostgreSQL и отправляет её UUID в `payload`. Оба исхода платёжной формы возвращают пользователя на `/dashboard?topUp=<UUID>`. Кабинет читает состояние через `GET /api/me/top-ups/{id}` и обновляет баланс после зачисления. Доступ к попытке проверяется по её текущему владельцу.

## Подтверждение и сверка

- `POST /api/webhooks/platega` принимает JSON по HTTPS. Spring Security разрешает этот маршрут без JWT. Обработчик проверяет `X-MerchantId` и `X-Secret` по `PAY_MERCHANT_ID` и `PAY_SECRET`.
- Обычно платёж находится по `provider_payment_id`. Если ответ на создание потерян, обработчик находит сохранённую попытку по `payload`, сверяет сумму, валюту и метод и привязывает ID Platega.
- Вебхук, фоновая сверка и ручная проверка в Telegram применяют статус через общий сервис. Он блокирует платёж и атомарно записывает зачисление, проводку и реферальные начисления. Повторный `CONFIRMED` ничего не начисляет. Уведомления Telegram отправляются после коммита.
- `CANCELED` закрывает неоплаченную попытку. Поздний `CONFIRMED` может её зачислить. После зачисления запоздалый `CANCELED` игнорируется.
- Споры и возвраты сохраняются для ручной сверки. При `CONFIRMED` после `DISPUTED` актуальный статус проверяется через API Platega. Возвраты и реферальные корректировки выполняются вручную.
- После таймаута создания сохранённая попытка остаётся доступной для сверки. Повтор с её UUID не создаёт новую транзакцию Platega. Для сверки искать заявку по UUID в `platega_payments.request_id`, затем сверить ID провайдера и проводки. При необходимости повторить доставку из кабинета Platega.

## Настройка после выкладки

1. При необходимости задать `WEB_PAYMENT_RETURN_URL` и `WEB_PAYMENT_METHODS` в окружении бэкенда. По умолчанию используются `https://crumpapp.xyz/dashboard` и `2,11`. Проверьте, что оба способа включены у мерчанта.
2. В настройках мерчанта Platega указать `https://crumpapp.xyz/api/webhooks/platega`. Действующий маршрут nginx `/api/` направляет запрос на бэкенд.
3. Провести тестовый платёж с телефона. Проверить возврат в кабинет, изменение баланса после вебхука и отсутствие повторных проводок после повторной доставки. С резервной фоновой проверкой платёж также зачисляется при пропуске вебхука.
