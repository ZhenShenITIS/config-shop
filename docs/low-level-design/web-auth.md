# WEB-01: основа web-аутентификации

Реализованы схема web-профилей и refresh-токенов, проверка access JWT и `GET /api/me`.
Регистрация, выдача токенов при входе, refresh/logout, подтверждение email и привязка
Telegram относятся к следующим задачам. Публичного endpoint для выпуска JWT пока нет.

## Данные

Миграция `004-web-auth.sql` добавляет `web_users` и `web_refresh_tokens`, не создавая
профилей для существующих пользователей бота. Один web-профиль связан с одним
`Account`: `account_id` имеет ограничения NOT NULL, UNIQUE и FOREIGN KEY.
В JPA это обычный UUID, без загрузки графа аккаунта и подписок.

Уникальность email проверяется по `lower(email)`. Нормализация и проверка адреса
будут выполняться при регистрации. Подтверждение хранится в `email_verified_at`:
NULL означает неподтверждённую почту. Статусной модели web-пользователя нет.

Refresh-токены представлены хешем SHA-256 (64 hex-символа), пользователем,
семейством, сроком действия, временем использования/отзыва и ссылкой на замену.
Выпуск, ротация и отзыв в WEB-01 не реализуются.

При реализации регистрации новый `Account` и `WebUser` нужно создавать в одной
транзакции через существующий `AccountService`. При привязке Telegram используется
уже существующий аккаунт.

## Настройки

Обязательна переменная `WEB_AUTH_JWT_SECRET_BASE64`: Base64 как минимум 32 случайных
байт. Отсутствующий, некорректный или слишком короткий ключ останавливает запуск.
Создать ключ можно командой `openssl rand -base64 32`; его нужно сохранить в
окружении сервера. Новый ключ при каждом запуске генерировать не следует.

Дополнительные переменные:

| Переменная | Значение по умолчанию |
|---|---|
| `WEB_AUTH_ISSUER` | `config-shop` |
| `WEB_AUTH_AUDIENCE` | `config-shop-web-api` |

## Access JWT

Подпись — только HS256. Обязательны `iss`, `aud`, `sub`, `account_id`, `iat`, `exp`.
`sub` — UUID web-пользователя, `account_id` — UUID его аккаунта. Срок между `iat`
и `exp` — не более 15 минут. Проверяются подпись, issuer, audience, срок действия,
`nbf`, если задан, и формат идентификаторов. Допуск рассинхронизации часов —
60 секунд. Email и хеш пароля в JWT не входят.

JWT передаётся только в `Authorization: Bearer …`. Сервер не использует HTTP-сессии
для аутентификации API и не принимает токен из query-параметров или cookie.
После проверки JWT загружается web-профиль и проверяется совпадение аккаунта.
Удалённый профиль или несовпадение аккаунта дают 401.

Подтверждение email будет проверяться при входе и refresh. WEB-01 не выдаёт JWT
и не вводит дополнительных состояний или блокировок профиля.

`GET /api/me` возвращает `webUserId`, `accountId`, `email`, `emailVerifiedAt`.
Идентификатор аккаунта из параметров запроса не используется. Пароль и refresh-токены
в ответ не включаются. Ошибки безопасности API возвращаются как JSON:
`{"error":"unauthorized"}` (401) и `{"error":"forbidden"}` (403).

## HTTP-маршруты

`/api/**` защищены Bearer-аутентификацией. В этой цепочке CSRF отключён, поскольку
API не использует автоматически отправляемые браузером credentials.
При добавлении refresh/logout с cookie нужна отдельная приоритетная цепочка
для соответствующих auth-маршрутов с CSRF-защитой.

POST `/webhook` и `/internal/remnawave/webhook` доступны без JWT и CSRF-токена.
Проверка подписи Remnawave остаётся в его обработчике. GET `/actuator/health`,
`/actuator/prometheus`, `/actuator/info` доступны как прежде для Docker и мониторинга.
Остальные маршруты вне API закрыты.

## Проверка

`./mvnw --batch-mode --no-transfer-progress verify` запускает тесты. Миграция,
ограничения БД, соответствие JPA и полный сценарий JWT → PostgreSQL → `/api/me`
проверяются через Testcontainers PostgreSQL 17; для этих тестов нужен Docker.
Без Docker они пропускаются. HTTP-тесты JWT выполняются и без Docker, с настоящими
подписанными токенами. Тестовые Spring-контексты используют профиль `dev`, чтобы
не обращаться к внешнему Loki.
