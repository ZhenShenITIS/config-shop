# Liquibase

## Что подключено

- Главный changelog: `src/main/resources/db/changelog/db.changelog-master.yaml`.
- Начальная миграция: `changes/001-initial-schema.sql`, структура из дампа `shop_db_20261018_154055.dump`.
- Включены 21 таблица, индексы, ограничения и identity-последовательности, в том числе Quartz.
- Пользовательские данные, владельцы и права из дампа в миграцию не входят.
- Liquibase применяет изменения при запуске, Hibernate только проверяет схему (`validate`).
- После 002 тарифы и пакеты трафика рассчитываются из конфигурации; инициализаторы таблиц удалены.

## Первое подключение существующей БД на сервере

Выполнять из корня проекта после сверки структуры рабочей БД с начальной миграцией. `changelog-sync` не проверяет их совпадение.

1. Собрать новый образ: `docker compose build app`.
2. Остановить бота: `docker compose stop app`; контейнер `postgres` оставить работающим.
3. Сделать свежий резервный дамп.
4. Однократно зарегистрировать **только начальную миграцию**:

```bash
docker run --rm \
  --network container:postgres \
  --env-file .env \
  --env LIQUIBASE_URL=jdbc:postgresql://localhost:5432/shop_db \
  --mount "type=bind,src=$PWD,dst=/workspace,readonly" \
  --workdir /workspace \
  maven:3.9.6-eclipse-temurin-21 \
  mvn -B liquibase:changelogSync \
    -Dliquibase.changeLogFile=db/changelog/db.changelog-baseline.yaml
```

Команда использует `POSTGRES_USER` и `POSTGRES_PASSWORD` из `.env`. Бота не запускает, рабочие таблицы и данные не меняет; создаёт служебные таблицы Liquibase и запись о начальной миграции.

5. При успешной синхронизации запустить новый образ: `docker compose up -d --no-deps app`.
6. Проверить логи: `docker compose logs --tail=100 app`.

Если синхронизация завершилась ошибкой, новый образ не запускать до выяснения причины. Начальная миграция намеренно останавливается на непустой схеме без предварительной регистрации.

`db.changelog-baseline.yaml` оставить неизменным: новые миграции подключать только в `db.changelog-master.yaml`. Повторная синхронизация общего changelog может ошибочно отметить будущие изменения выполненными.

## Переход на аккаунты — 002-account-schema

В master подключён `changes/002-account-schema.sql`. Он выполняется одной транзакцией: переименовывает 10 старых бизнес-таблиц в `old_*`, создаёт 11 таблиц новой модели, переносит данные, восстанавливает журнал и проверяет балансы. Quartz и служебные таблицы Liquibase сохраняются. `migration_id_map` хранит соответствия старых ID новым UUID, включая старые кнопки выводов. `migration_report` хранит расхождения, неизвестные даты и результаты сверки.

Тарифы теперь рассчитываются из конфигурации по прежним формулам. Новые покупки устройств сохраняют тип `DEVICE`. Новая ценовая политика, пересчёт срока при смене устройств и web-таблицы в эту миграцию не входят. Коэффициенты аккаунта зарезервированы схемой; действующие покупки используют `account_price_rate = 1`.

До выпуска:

1. Восстановить свежий дамп в отдельной PostgreSQL 17. Выполнить `docs/database/preflight.sql` на старой схеме. Это диагностика без изменений данных; окончательная проверка всех связей и ограничений выполняется при переносе.
2. Если на сервере ещё не зарегистрирована 001, выполнить однократный baseline по инструкции выше. Повторный `changelogSync` для master не выполнять.
3. Проверить тесты: `./mvnw clean test`. Для репетиции конкретного дампа: `./mvnw -Dtest=LiquibaseMigrationTest#rehearsesMigrationOnSuppliedDumpInIsolatedPostgres -Dmigration.dump=/absolute/path/shop.dump test`. Дамп восстанавливается только во временном тестовом контейнере.
4. Собрать образ, остановить все экземпляры бота и фоновые обработчики, снять финальный резервный дамп. Запустить новую версию: Liquibase завершит перенос до проверки JPA и запуска обработчиков. Не запускать старую версию параллельно с новой.
5. Проверить журнал миграции и отчёт запросами ниже. Оставить `MIGRATION_NOTIFICATION=false`: старые Quartz-задания поддерживаются и получают срок конкретной подписки из панели при исполнении; массовое пересоздание заданий не требуется.
6. Проверить профиль, покупку/продление, трафик, устройства, пополнение, промокод, реферальный список, вывод и историю. Сохранить `old_*` и маппинги до завершения проверки.

```sql
-- Сверка должна вернуть 0.
SELECT count(*) FROM (
    SELECT u.id FROM old_bot_users u
    JOIN bot_users b ON b.telegram_id = u.id
    LEFT JOIN balance_log l ON l.account_id = b.account_id
    GROUP BY u.id, u.balance
    HAVING coalesce(sum(l.amount), 0) <> u.balance
) differences;

SELECT reason, count(*) FROM migration_report GROUP BY reason ORDER BY reason;
SELECT old_id, old_balance, reconstructed_balance, correction
FROM migration_report
WHERE reason = 'BALANCE_RECONCILIATION' AND correction <> 0;
```

Старые платежи без подтверждённого владельца остаются в `old_platega_payments` и отчёте `UNRESOLVED_OWNER_MANUAL_REVIEW`. Их старые кнопки предлагают обратиться в поддержку. Принятый риск не блокирует перенос. Количество таких строк не означает количество оплаченных платежей.

Если старое EXTERNAL-пополнение уже существует, но статус платежа ещё `PENDING`, сохраняются и пополнение, и исходный статус. Расхождение отражается как `CREDITED_PAYMENT_STATUS_PENDING`. Проверка оплаты видит существующее пополнение и не зачисляет его повторно; статус провайдера автоматически не выдумывается.

Для ручной обработки действительно оплаченного неперенесённого платежа сначала подтвердить у провайдера его ID, сумму, валюту и владельца и проверить отсутствие зачисления в `old_top_ups` и новом `top_ups`. Восстановить только запись платежа в новой `platega_payments` с проверенным `account_id` и исходным `provider_payment_id`, используя сохранённый маппинг ID; не создавать дубликат существующего платежа. Затем повторить обычную проверку оплаты старой кнопкой: `PaymentService` проверит провайдера, а `BalanceService` создаст EXTERNAL-пополнение и запись журнала. Уникальность `provider_payment_id` и `top_ups.platega_id` исключает повторное зачисление. Прямое изменение баланса SQL не требуется.

При ошибке 002 откатывается целиком. После успешного переноса и появления новых операций возврат одного старого образа небезопасен: нужен согласованный перенос новых операций обратно либо восстановление резервной копии с отдельным разбором последующих оплат.

Репетиция на `shop_db_20261018_154055.dump`: 758 аккаунтов, итоговые балансы совпали у всех; 6 ненулевых ADMIN-корректировок; 261 исторический платёж без владельца оставлен в архиве; один уже зачисленный платёж с `PENDING` сохранён без повторного начисления. Перед выпуском повторить на свежем дампе.
