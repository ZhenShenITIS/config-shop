


# Миграция

## Старые таблицы
Предварительно для всех старых бизнесовых таблиц провести миграцию с переименовыванием на old_table_name. В будущем учесть занятые имена индексов и identity-последовательностей старых таблиц.


### old_bot_users
Для каждой записи создаем записи в таблицах
bot_users
- updated_at = old_bot_users.created_at
- Остальные поля однозначно соответствуют old_bot_users

remnawave_subscriptions
- created_at = old_bot_users.created_at
- id генерируемый
- Остальные поля соответствуют однозначно old_bot_users

accounts
- id генерируемый
- updated_at = old_bot_users.created_at
- Остальные поля однозначно соответствуют old_bot_users

На время миграции полагаем соотвествие 1 account = 1 remnawave sub
Новая связь `telegram_id → account_id → remnawave_subscription_id`.

### old_referrals
Переносим данные в таблицу referrals
Для каждой записи из old_referrals
- id генерим
- referrer джойним + группируем account + bot_ids по id тг
- referral джойним + группируем account + bot_ids по id тг
- created_at соответствует

### old_purchases
Для каждой записи создаем запись в purchases
- id генерируем
- sub_days/sub_devices получаем из old_subscriptions путем джоина с old_purchases по subscription_id
- traffic_gb и device_count соответствуют однозначно
- remnawave_subscription_id получаем джоинами по bot_user_id
- type = purchase_type
- account_id - аналогично рефералам
- Остальное 1 к 1


###  old_top_ups
для каждой записи из этой таблицы создаем запись в top_ups
- account_id - аналогично рефералам
- referral - аналогично рефералам
- Для EXTERNAL-пополнений связываем platega_id с перенесённым реальным платежом из old_platega_payments по external_id = transaction_id. Не создаём вымышленные платежи по произвольному external_id: у промокодов это поле имеет другой смысл.

### old_platega_payments
- Переносим платежи с подтверждённым владельцем; сохраняем transaction_id как provider_payment_id.
- Старые PENDING без подтверждённого владельца оставляем в архиве old_platega_payments и включаем в отчёт. Они не блокируют переход; риск ручной обработки 1–2 оплат принят.
- Подтверждённые оплаты из этого отчёта при необходимости зачисляем вручную через BalanceService с записью источника и исключением повторного начисления. Не назначаем владельца без проверки.
- Для новых платежей account_id обязателен. Промежуточный релиз для восстановления владельцев не требуется.

### old_withdrawals
Для каждой создаем withdrawals
account_id аналогично рефералам
updated_at проставляем как created_at

### Переключение бота

- Перед переключением выключить бота и снять свежий дамп БД
- Telegram ID использовать для поиска аккаунта; бизнес-операции выполнять по `account_id`.
- Перевести профиль, регистрацию, платежи, покупки, рефералы, промокоды, выводы и фоновые задачи на новую модель.
- Удалить реферальные функции, завязанные на expireAt, без замены запросами в Remnawave. Остальные реферальные функции сохранить.
- Сохранить покупку дополнительных устройств по старому флоу и текущие формулы цен. Новую политику ценообразования и пересчёт срока при смене устройств не реализовывать.
- Ограничить задачу необходимыми изменениями для перехода на новую схему; подробный порядок — в code-migration-plan.md.
- Все изменения баланса проводить через единый сервис и журнал; защитить от повторных зачислений и одновременного перерасхода.
- Подготовить изменения по сценариям, но переключить все денежные операции согласованно, без двух независимых источников баланса.
