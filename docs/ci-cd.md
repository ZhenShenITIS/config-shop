# CI/CD через GitHub Actions

При push в `module-arch` workflow `.github/workflows/ci-cd.yml`:

1. Собирает проект и запускает `./mvnw verify` на Java 21 в GitHub. Для интеграционных тестов используется Docker на runner.
2. После успешных тестов подключается по SSH к VM как `paneluser` с паролем из Actions Secrets.
3. Через `sudo` выполняет скрипт деплоя от root в `/root/config-shop`.
4. Обновляет checkout до проверенного коммита через fast-forward.
5. Выполняет `docker compose build app`.
6. Создаёт и проверяет полный дамп PostgreSQL перед запуском новой версии.
7. Пересоздаёт `app` и ждёт успешного `/actuator/health` до 180 секунд.

Бэкап структуры и всех данных `shop_db` сохраняется на VM в `/root/config-shop/backups/shop_db_<дата UTC>_<коммит>_<случайный суффикс>.dump`. Используется сжатый архив `pg_dump --format=custom`, читаемый через `pg_restore`. Учётные данные берутся из окружения работающего контейнера `db`. Файл имеет права `600` и не попадает в Git.

Перед сохранением архива скрипт проверяет, что он не пустой, и полностью читает его через `pg_restore --file=/dev/null`, без подключения к БД. При ошибке дампа или проверки деплой останавливается до пересоздания `app`, временный файл удаляется. Успешный бэкап сохраняется и при последующей ошибке запуска приложения. Старые бэкапы автоматически не удаляются.

В pull request в `module-arch` выполняются только проверки. Деплои выполняются последовательно; устаревший запуск пропускается, если ветка уже ушла вперёд. При push новой версии текущая сборка и деплой не прерываются. Результат виден на вкладке **Actions** репозитория.

Сборка образа остаётся на VM, как при ручном обновлении. Обновление занимает время тестов, сборки и запуска. При пересоздании единственного контейнера будет короткий перерыв в работе.

## 1. Настройки GitHub

Откройте **Settings → Secrets and variables → Actions** репозитория.

На вкладке **Secrets → New repository secret** добавьте:

| Name | Значение |
| --- | --- |
| `DEPLOY_PASSWORD` | Пароль SSH-пользователя `paneluser`; по умолчанию он же используется для `sudo` |
| `DEPLOY_SUDO_PASSWORD` | Необязательно: пароль для `sudo`, только если он отличается от пароля SSH |
| `DEPLOY_KNOWN_HOSTS` | Проверенная запись SSH-ключа самой VM в формате `known_hosts`; получение описано ниже |

В обычной конфигурации `sudo`, как в запросе `[sudo] password for paneluser`, нужен пароль **paneluser**, а не пароль root. Личные SSH-ключи для подключения Actions создавать не требуется.

На вкладке **Variables** добавьте:

| Name | Значение |
| --- | --- |
| `DEPLOY_HOST` | Внешний IP или DNS-имя VM |
| `DEPLOY_USER` | `paneluser` |
| `DEPLOY_PATH` | `/root/config-shop` |
| `DEPLOY_PORT` | SSH-порт; при отсутствии используется `22` |

Пароли хранятся в Secrets, отдельно от файлов и истории Git. Workflow получает их через переменные окружения: `sshpass -e` использует пароль для входа, а `sudo -S` получает пароль через стандартный ввод. Пароль не включается в команду, передаваемую серверу. Workflow с доступом к секретам может использовать их, поэтому право менять workflow и делать push в ветку деплоя означает доверенный доступ к развёртыванию.

## 2. Проверка SSH-ключа сервера

`DEPLOY_KNOWN_HOSTS` проверяет, что Actions подключается к нужной VM. Это публичная запись существующего ключа сервера; создавать свою пару ключей не нужно.

На своём компьютере, подставив адрес и SSH-порт, выполните:

```bash
ssh-keyscan -p 22 -t ed25519 VM_HOST > config_shop_vm_known_hosts
ssh-keygen -lf config_shop_vm_known_hosts
```

Сравните fingerprint с выводом через консоль VM или уже доверенное подключение:

```bash
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

После совпадения вставьте содержимое `config_shop_vm_known_hosts` в Secret `DEPLOY_KNOWN_HOSTS`. Адрес и порт должны совпадать с Variables. `ssh-keygen -lf` здесь только показывает fingerprint, новый ключ эта команда не создаёт.

## 3. Проверка VM

Подключитесь привычным способом как `paneluser`. Пользователю должен быть разрешён вход по SSH с паролем и выполнение root-команд через `sudo` без обязательного TTY. Workflow использует `sudo -k -S -p '' -H -- bash`: запрашивает новую проверку пароля, передаёт его через stdin и задаёт домашний каталог root. Интерактивный `sudo su` для автоматизации не требуется.

Проверьте окружение root:

```bash
sudo -H bash
cd /root/config-shop
git branch --show-current
GIT_TERMINAL_PROMPT=0 GIT_SSH_COMMAND='ssh -o BatchMode=yes' git fetch --no-tags origin module-arch
git status --short
docker info
docker compose version
docker compose up --help
test -f .env
exit
```

Checkout должен быть на `module-arch`. Если сейчас выбрана другая ветка, переключитесь на неё вручную после разбора локальных изменений. Скрипт останавливается при изменениях отслеживаемых файлов и при расхождении истории; игнорируемый `.env` этим проверкам не мешает.

Нужен Docker Compose v2 с опциями `--wait` и `--wait-timeout`. PostgreSQL и остальные сервисы уже должны работать. Сохраните существующий каталог и настройки Compose project name, если задавали их вручную: они определяют используемые контейнеры и volumes. Нужный `COMPOSE_PROJECT_NAME` можно указать в серверном `.env`, поскольку переменные интерактивного shell в Actions автоматически не передаются.

Доступ **VM → GitHub** для `git fetch` настраивается отдельно от входа **Actions → VM**. Используйте существующий доступ root, с которым работает ручной pull. Он должен работать без запросов ввода; для приватного репозитория по HTTPS нужны сохранённые учётные данные GitHub с доступом к чтению репозитория. Пароль `paneluser` не является паролем для GitHub.

SSH-порт VM должен быть доступен GitHub-hosted runner. При ограничениях firewall нужен разрешённый сетевой маршрут, например runner в вашей сети.

## 4. Конфигурация приложения

Серверный `.env` остаётся в `/root/config-shop/.env`. Compose читает его на VM; GitHub запускает сборку и тесты без production-конфигурации приложения. Fast-forward не изменяет игнорируемый `.env`; `.env_dist` служит примером и не копируется поверх него.

Для изменения токена, URL, цены или другого значения отредактируйте `.env` на VM и пересоздайте контейнер:

```bash
sudo -H bash
cd /root/config-shop
nano .env
docker compose up -d --no-deps --no-build --force-recreate --wait --wait-timeout 180 app
exit
```

Обычный `docker compose restart app` не перечитывает переменные окружения из `.env`. Пересборка образа для изменения runtime-переменных не требуется. При добавлении обязательной переменной в код добавьте её значение в серверный `.env` до деплоя и пример в `.env_dist`. Изменения переменных для Grafana применяйте пересозданием `grafana`; изменение пароля PostgreSQL в `.env` само по себе не меняет пароль в уже созданной БД.

`.gitignore` исключает `.env`, `.env.*`, `/full_backup.sql` и `/backups/`. Правила не действуют на уже отслеживаемые файлы. Под root из каталога проекта можно проверить только имена таких файлов, не выводя содержимое:

```bash
git ls-files -- .env .env.save full_backup.sql backups
```

## 5. Первый запуск и диагностика

После настройки сохраните изменения CI/CD в Git и выполните push в `module-arch`. На вкладке **Actions** должны последовательно завершиться **Build and test** и **Deploy to VM**. Последующие push запускают ту же цепочку автоматически.

Если SSH возвращает `Permission denied`, проверьте адрес, порт, `DEPLOY_USER`, `DEPLOY_PASSWORD` и разрешён ли вход по паролю. Ошибки `sudo` проверяйте отдельно: пароль, права `paneluser` на выполнение root-команд и отсутствие требования терминала.

Если пересборка образа, создание или проверка бэкапа не удались, старый контейнер продолжает работать. Если ошибка произошла после пересоздания контейнера, workflow завершится с ошибкой; автоматический откат не выполняется. Проверьте на VM:

```bash
sudo -H bash
cd /root/config-shop
docker compose ps app
docker compose logs --tail=100 app
exit
```

Деплой обновляет сервис `app`. Изменения конфигурации PostgreSQL и мониторинга применяйте отдельно. Liquibase выполняет миграции при старте приложения; для первой миграции существующей БД и резервного копирования используйте [инструкцию Liquibase](database/liquibase.md).

Документация GitHub: [Actions Secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets).
