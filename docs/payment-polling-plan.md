# Фоновая проверка пополнений

Цель: оплаченный платёж зачисляется без нажатия кнопки пользователем.

Реализовано.

1. **Общая проверка.** Кнопка и фон используют одну логику. Проверку владельца при вызове пользователем сохраняем.
2. **Транзакция.** Запрос к Platega выполняем вне транзакции. Затем блокируем платёж, повторно проверяем состояние и атомарно сохраняем статус, пополнение и реферальные начисления. Повторное зачисление исключаем существующими проверками и ограничениями БД.
3. **Ответ Platega.** Получаем и сверяем ID, сумму и валюту перед зачислением.
4. **Фоновая проверка.** Spring `@Scheduled` вызывает один метод обхода платежей. Интервал между завершением обхода и следующим запуском задаётся в `application.properties`: `payments.polling.interval` (по умолчанию `30s`, можно переопределить через `PAYMENTS_POLLING_INTERVAL`). Выбираем все PENDING без зачисления, порциями с курсором; добавляем индекс для этой выборки. Состояние обработки хранится в `platega_payments` и `top_ups`. Отключение: `payments.polling.enabled=false`.
5. **Ошибки.** Логируем сбой платежа и продолжаем обход; повторяем проверку в следующем цикле. При 429 учитываем Retry-After. По возрасту платёж не отменяем. После рестарта продолжаем обработку из БД.
6. **Кнопка после зачисления.** Возвращаем CONFIRMED вместо нынешнего EXPIRED, повторных начислений и событий не создаём.
7. **Уведомление.** После commit отправляем сообщение о зачисленной сумме с кнопкой главного меню. Для аккаунта без Telegram сообщение пропускаем; ошибка доставки не влияет на зачисление.

Проверки: оплата без кнопки; одновременная проверка кнопкой и фоном; откат при ошибке рефералов; сбой Platega; обход нескольких порций; восстановление после рестарта.

На этом этапе — один экземпляр приложения. Вебхуки и автоматическую обработку возвратов откладываем.
