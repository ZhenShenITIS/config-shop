# Введение

## 1. Глоссарий

- **remnawave** — https://docs.rw/ — панель для администрирования VPN. Предоставляет мощный функционал, а также удобные эндпоинты.
- **platega.io** — платежная система, интегрированная в проект.
- **Подписка** — сущность панели remnawave, по сути заменяет собой сущность User для remnawave, к ней привязываются лимиты трафика, дни устройства и тд.

## 2. Описание проекта

Сервис представляет из себя телеграм-бота для покупки и управления подписки на VPN.

Сетевое администрирование, а именно управление серверами, трафиком, подключениями и подписками происходит на стороне внешнего сервиса Remnawave.

### 2.1. Конкуренты

- https://dendivpn.shop/
- https://wisekeys.net/
- https://phantom.direct/

### 2.2. Функционал бота

- пополнение баланса;
- оплата подписки;
- история операций;
- покупка дополнительных ГБ трафика и устройств;
- управление устройствами;
- реферальная система;
- применение и создание промокодов;
- контакты технической поддержки;
- получение информации о сервисе путём массовой рассылки пользователям;
- базовое администрирование балансов пользователей для сотрудника технической поддержки;
- уведомления о скором окончании подписки и реферальных пополнениях.

### 2.3. Технический стек

- Java 21;
- Spring Boot 4.0;
- Spring Data JPA;
- PostgreSQL.

## 3. Существующие проблемы

- Наспех написанный код, включающий такие проблемы как:
  - сетевые вызовы в транзакциях;
  - отсутствие миграции (ddl.auto = update);
  - неправильное разделение логики по слоям приложения;
  - разрозненное деление по пакетам.
- Телеграм недоступен без ВПН, что затрудняет покупку для новых пользователей и пользователей, забывших вовремя продлить подписку.
- Баги с засчитыванием оплаты.
- Непроработанность системы пересчета устройства при продлении подписки. Количество устройств сохраняется по тому количеству, которое пользователь приобрёл при последнем продлении подписки. В связи с этим возможна такая ситуация:
  1. Пользователь покупает подписку на 12 месяцев на 3 устройства за 2000р.
  2. Пользователь продляет подписку на месяц на 10 устройств за 600р.
  3. Пользователь получает подписку на 13 месяцев на 10 устройств за 2600р, вместо 5000.

## 4. Решение

Решением проблемы доступности телеграмма является написание сайта с аналогичным функционалом и дальнейшее размещение сайта на серверах, доступных в ограничениях сети.

Целевое решение должно иметь вид модульного SpringBoot-проекта со следующим разделением:

- логика работы с телеграмом без бизнес-логики;
- бэкенд сайта с слоем эндпоинтов для фронтенда;
- ядро системы, представляющая собой чистую бизнес-логику, а также слой работы с данными.

Так как слой логики работы с телеграмом уже написан и по большей части писался в отрыве от основной бизнес-логики сервиса, предлагается сохранить эту часть кода в целевом решении. Нет смысла переписывать код обработки коллбеков, команд и рендеринга сообщений, так как он не имеет проблем, описанных выше. Вместо этого, необходимо заменить вызовы сервисного слоя в классах команд на вызовы методов интерфейсов модуля ядра системы.

### 4.1. Функциональные требования

- Система предоставляет пользователю бесшовный опыт взаимодействия: клиент может зарегистрироваться на сайте, пополнить баланс, купить подписку. Параллельно зарегистрироваься в боте, пополнить баланс купить подписку. Потом связать эти 2 аккаунта в один и в этом случае балансы должны складываться и в личном кабинете пользователя на сайте должна появиться вторая подписка с возможностью мёрджа двух подписок с выбором нескольких вариантов.
- Слияние аккаунтов и слияние подписок это разные бизнес-кейсы.
- Сайт предоставляет удобный UX с возможностью легко найти и изучить нужные инструкции по подключению. Ориентируемся на то, что нашим продуктом сможет воспользоваться человек, который впервые узнал что такое ВПН, его цель - продолжать вести переписки в телеграмме.
- Пользователь имеет возможность сделать ярлык на рабочем столе, ведущий на сайт. При наличии непрочитанных уведомлений на ярлыке появляется соответствующая иконка.

### 4.2. Нефункциональные требования

- Система проектируется в парадигме DDD.
- ЯП модулей бэкенда сайта и кор-логики является Kotlin.
- Сервис выдерживает нагрузку 1 RPS.
- Провести денорамализацию текущих таблиц сервиса под новую архитектуру: вынести из сущности bot_user всю информацию, не связанную с телеграмом и сделать связь с новой сущностью account.
- Миграция существующих юзеров не должна привести к неконсистентности данных.
- Поменять систему подсчета баланса: источником правды является общий лог транзакций.
- Весь функционал сохранен.

### 4.3. Оставшиеся вопросы

Для организации пополнения баланса необходимо решить проблему доступности сайта платежной системы в условиях ограничения мобильной сети. Предполагаемые решения для проработки:

- Написание страницы-прокси, которая будет размещена на наших серверах высокой доступности.
- Поиск другой платежной системы, сервера которой доступны в условиях ограничения мобильной сети.

## 5. Пользовательские сценарии

### 5.1. Регистрация на сайте

1. Нажатие кнопки регистрация.
2. Поля регистрации — почта, пароль, реферальный код.
3. В случае перехода на регистрацию с реферальной ссылки, код подставляется автоматически.
4. При использовании реферального кода производится доменное событие, которое тригерит систему рефералов:
   1. Происходит пересчет рефералов на 3 уровнях.
   2. Соответствующим реферерам присылается уведомление о регистрации нового рефералаа.
5. Отправляется письмо для подтверждения почты.
6. После подтверждения почты создается и выдается пробная подписка (без подтверждения почты в ремну даже не пойдем).

### 5.2. Пополнение баланса

1. Юзер нажимает на баланс.
2. Появляется под ним кнопка пополнить.
3. При нажатии на кнопку пополнить появляется окно пополнения баланса.
4. В окне пополнения баланса можно ввести сумму, выбрать способ оплаты (по умолчанию СБП).
5. Сумма пополнения должна быть не меньше 100р и мы предлагаем 4 суммы для быстрого ввода (конкретные числа будут посчитаны позднее на основе существующих данных).
6. После настроек оплаты становится активной кнопка "Продолжить пополнение".
7. После нажатия на кнопку генерируется ссылка на оплату, на которую пользователь редиректится.
8. Оплата засчитывается с помощью вебхуков от платежной системы.
9. Пополнение баланса производит соответствующую запись в БД.
10. Если у пользователя, пополнившего баланс есть рефереры, то в БД создадутся записи о начислении им реферального бонуса в соотвествии с уровнем реферала.
11. Реферальное пополнение триггерит уведомление о реферальном пополнении.

### 5.3. Продление подписки

1. В разделе продления подписки появляются два ползунка с выбором: месяцы, устройства.
2. Внизу итоговая сумма.
3. Пользователь может оплатить подписку только с баланса своего счета. При недостаточном балансе пользователь переходит в окно пополнения баланса, флоу которого уже описан выше.
4. После покупки подписки отправляется соотвествующий запрос в ремнавейв и подписка обновляется.
5. Покупка подписки провоцирует создание отложенной задачи за 3 и за 1 день до окончания подписки.
6. Задача присылает соответствующее веб-уведомление.
7. При продлении подписки старые задачи удаляются.

### 5.4. Докупка устройств

1. Если у пользователя больше или равно 10 устройств в выбранной подписке, то кнопка покупки устройств у этой подписки будет неактивна, если пользователь попробует руками собрать запрос, то получит исключение.
2. В окне докупки устройств появляется ползунок от 1 до (10-N), где N — количество устройств пользователя. В случае сложностей с реализацией динамического ползунка можно использовать кнопки.
3. Внизу итоговая сумма. Сумма рассчитывается в зависимости от оставшихся дней подписки.
4. После покупки устройств отправляется соотвествующий запрос в ремнавейв.

### 5.5. Докупка трафика

1. В окне докупки трафика можно выбрать пакет трафика или ввести собственное кастомное число.
2. На пакетах в углу указана скидка в процентах от базовой покупки.
3. При вводе кастомного числа также применяется скидка в соответствии со скидками на пакеты. Скидка при кастомной покупке не может превосходить скидку максимального пакета.
4. Внизу итоговая сумма.
5. После покупки устройств отправляется соотвествующий запрос в ремнавейв.

## 6. Разделы на сайте

### 6.1. Просмотр статистики подписки

1. Статистика по текущей подписке (или подпискам) пользователя должна быть на главной странице сайта для авторизованных пользователей.
2. Для отображения статистики выполняется запрос в ремнавейв.

### 6.2. Покупка

1. В окне статистики по каждой подписке есть кнопки "Продлить подписку", "Докупить ГБ" и "Докупить устройства". Если у пользователя нет подписки, то предлагается её приобрести.
2. При нажатии на продление подписки/ГБ/устройства у пользователя появляется окно продления подписки/ГБ/устройства.
3. В верхней части этого окна можно переключиться между вкладками продления подписки, докупки трафика и устройств (нужно для того, чтобы не нажимать назад).
4. В окне покупки устройств есть подпись о лимите в 10 устройств в одной подписке.

### 6.3. Управление устройствами

1. Через окно подписки можно открыть окно со списком устройств.
2. В списке устройств можно удалить любое устройство.
3. Отправляется соотвествующий запрос в ремнавейв.

### 6.4. Просмотр истории операций

На сайте есть отдельная вкладка, которая показывает общий лог операций пользователя.

### 6.5. Промокоды

На сайте реализован отдельный раздел для создания и применения промокодов.

Детали реалзиации будут продуманы в дальнейшем.

### 6.6. Связь с технической поддержкой

1. На сайте реализован непрерывный диалог с технической поддержкой с возможностью прикладывать файлы и изображения.

### 6.7. Уведомления

1. На сайте реализована отдельная вкладка для уведомлений о скором окончании подписки, реферальных начислениях и новостях проекта.

## 7. Оформление

1. Сайт должен быть выполнен в белой теме по умолчанию.
2. Акцентный цвет — светло-голубой, синий.

## 8. План реализации

Реализацию проекта следует поделить на несколько этапов. Первоначальным будет стадия MVP, закрывающая основную проблему — невозможность оплаты/продления без впн.

### 8.1. MVP

В рамках MVP должен быть реализован следующий функционал:

- Регистрация (с рефералкой).
- Пополнение баланса.
- Покупка подписки, устройств, трафика.
- Управление устройствами.
- Статистика подписки.
- Создание реферальных промокодов.
- Техническая поддержка в виде ссылки на ТГ аккаунт поддержки.

### 8.2. Stage 1

Доработки включают в себя:

- Уведомления о подписке, рефералах и новостях.
- Создание промокодов администратором.
- чат с технической поддержкой;
- **Оплата** в условиях ограничения мобильной связи;
- Применение обычных и реферальных промокодов.

## 9. Общие заметки

Для баланса и покупок можно использовать паттерн "Модель данных, основанная на событиях".
